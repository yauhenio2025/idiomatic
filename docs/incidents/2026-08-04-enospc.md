# 2026-08-04 — /data ENOSPC (second occurrence)

**Impact:** six deck builds failed with `OSError(28)`; the video worker
burned retry attempts on every claim until space freed (same failure
mode as 2026-07-27). No data loss.

**Detection:** exercises2/translation build batch returned
`No space left on device` in `grammar-status`.

**Diagnosis:** added read-only `/admin/disk-usage` (tree scan +
`?path=` per-file drill-down; first version 500ed — `is_file(
follow_symlinks=…)` is Python 3.13-only, container runs older).
Findings on the 10.46 GB disk at 0.0 free:
- ~4 GB rolling pool decks (`_pool_idioms/_pool_expressions` × 5 langs;
  legitimate product, grows monotonically with the idiom library);
- ~2.7 GB per-video apkgs, including six-week-old files: **orphan
  leak** — `/admin/purge-video` deletes the `apkgs` row, and the
  row-driven retention reaper then never sees the file again (the
  purged France24 decks from 2026-06-24 were still on disk);
- ~1 GB `_pool_stage` intermediates (self-cleaning, in-flight).

**Fix (deployed):** janitor gained `_sweep_orphan_video_apkgs`
(deletes `apkgs/*/​*.apkg` files with no DB row; `_`-prefixed rolling
decks never candidates; 1-day age guard); `apkg_retention_days`
30 → 12. Janitor freed ~1.7 GB on next worker start; all failed builds
re-ran clean (apkgs 1355-1361). End state: 8.97 GB used / 1.48 free.

**Lesson / watch item:** the pool decks alone will grow into the limit
again within months. Options when free space < ~1 GB: paid disk
upsize, or a delta-pool redesign (ship only recent/changed notes per
rolling apkg — the collection keeps everything; imports never delete).
Check `/admin/disk-usage` before commissioning any new audio-heavy
deck family.
