# Incident: recurring web-process hangs (2026-07-31) — ROOT CAUSE FOUND + FIXED

> RESOLUTION (16:35 +08): the "hangs" were the event loop of the web
> process blocking for the full duration of a post-video POOL REBUILD.
> `pool.rebuild_pools` (async) called the four deck builders — hundreds
> of blocking ffmpeg `subprocess.run` calls — directly on the event
> loop, no `asyncio.to_thread`. Small library = unnoticed blips;
> today's library size = 10-15 min total unresponsiveness per rebuild,
> self-resolving when the rebuild finished (hence "the hang follows
> successful work", hence Dutch counts complete, hence 100% CPU with
> zero logs, hence a 4th blockage during the NEXT video's es rebuild
> at 16:20 while the forensics below were being written). The LingQ
> sync was never the cause. Fixes shipped (three commits): builders run
> via asyncio.to_thread (46a118f); rebuilds serialized per language —
> the blocking loop had been serializing them by accident, and the
> first unserialized overlap corrupted its own staging files, which is
> almost certainly the "corrupt piece" that failed the 09:24 de
> rebuild; and a per-card stitch try/except so any bad mp3 costs one
> card its audio, never the 4-deck rebuild. VERIFIED 18:17 +08: full de
> rebuild (500 idioms, 28 min) and es rebuild (335 idioms, 37 min)
> completed with zero downtime and zero stitch failures; health probes
> green throughout. The only remaining blips are ~30 s deploy swaps.
> The historical record below is kept as written.

## What the logs and metrics settle

**The DB was never the problem.** During the 16:00 cron tick — which
ran BOTH the full LingQ self-heal (37,411 upserts across de/es/it/zh/
pt/sv, 08:01–08:08Z) AND the personal_errors registry ingest (11,481
upserts, 08:08:49Z) — the Postgres instance stayed at: memory 64→87 MB
(of 256), 2–3 active connections, CPU ≤5%. All cron work completed
cleanly; the cron container exited normally at 08:09:58Z.

**The hang is a CPU spin inside the WEB process, at the pool-rebuild
boundary of the video worker.** Timeline (UTC):

- 08:02:00 worker picks up de video 8kF0yFI_5vU (queued by an earlier
  tick; a normal video job).
- 08:02:46 ffmpeg errors on this video's own audio: `context_006.mp3` —
  "Failed to find two consecutive MPEG audio frames" / concat
  "Invalid data found when processing input" (corrupt clip; pipeline
  recovered and continued).
- 08:02:48.4 `apkg.written` → `worker.apkg_inserted id=1118` →
  `worker.pool_source_persisted` — the LAST log lines the process ever
  emitted. The next step in process_video is
  `pipeline/pool.py::rebuild_pools("de")`.
- 08:03 container memory jumps 122→215 MB and climbs to ~243 MB;
  **CPU pegs at 100% of the allotment from 08:04 and stays there 12+
  minutes with zero output** — not even uvicorn request lines for
  probes that were timing out. Instance count stayed 1 (no OOM kill,
  no restart).

A CPU-bound spin on the event-loop thread (or something holding the
GIL hard) starves uvicorn entirely — which matches the total silence:
the app can't even accept a TCP connection.

## Reinterpretation of the two LingQ-era hangs

Both prior hangs "followed successful work". Both coincided with
periods when the worker was also active. Given today's evidence —
bulk DB writes running FULLY cron-side while the web process hung
anyway — the LingQ sync was likely never the cause; the common factor
is the worker's post-video pool rebuild. The Dutch-complete
observation from the second hang fits the same shape: the sync
finished, then something else in the process spun.

## Prime suspects inside rebuild_pools (unproven, for the owner)

1. A retry/derive loop around corrupt staged audio (this video wrote a
   corrupt `context_006.mp3` moments earlier; if the pool stitcher
   loops on ffmpeg failure rather than skipping, that's a spin with
   growing memory from accumulated buffers).
2. genanki/zip packaging of the four de pool decks — CPU-heavy but
   should terminate; 12+ min at 100% with no completion makes a plain
   big-package less likely than a loop.
3. Something in loudness-normalization/stitching shelling ffmpeg with
   a full, undrained pipe (subprocess deadlock would show 0% CPU
   though — the observed 100% points at Python-side looping).

## Suggested next steps (owner's call)

- Reproduce locally: run `rebuild_pools("de")` against prod-shaped
  staged_audio including a deliberately corrupt clip; watch for the
  spin.
- Add a watchdog log line + hard timeout around each pool build stage
  (asyncio.wait_for on the to_thread call), so a future spin degrades
  to a logged failure instead of a frozen service.
- Consider moving pool rebuilds off the web process entirely (same
  containment as everything else); the debounce table already
  serializes them.
